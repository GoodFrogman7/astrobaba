# ADR-0005: Horoscope generation pipeline

- Status: Accepted
- Date: 2026-10-21

## Context

Horoscope pages (12 Moon signs × daily/weekly/monthly, with love, career, money and health)
bring search traffic. Their prose has to be readable, but PLAN.md is strict: astro facts come
only from the engine, LLMs only write prose around computed facts, and no LLM output reaches a
horoscope page without human QA (§0.4, §6). Scores use a fixed 5-step scale from rules, not
randomness.

## Decision

```
engine /v1/horoscope/facts ──> worker: prompt from facts only ──> LLM ──> validator
        (positions, houses from              (no new facts, no       │     (schema, length,
         the sign, rule-based scores)         fear, no advice)       │      banned claims,
                                                                     ▼      grounding)
                                            horoscope_entries (pending_review)
                                                                     │  human review
                                                                     ▼  (approve / edit / reject,
                                            horoscope_entries (published)      audit_log)
                                                                     │
web page ── facts (always) + published prose (if any) ◄──────────────┘
```

1. **Facts** come from the engine: graha positions for the period window (00:00 IST
   boundaries), houses counted from the Moon sign, sign ingresses, and five area scores.
   Scores are a weighted sum of favourable/challenging gochara houses from
   `data/astro/horoscope_rules.json`, mapped to 1-5 by fixed thresholds. Same input, same
   score. The rules are classical but conventions vary, so the file carries
   `needs_astrologer_review` and every page says the rules await review.
2. **Prose** is generated by the worker (`python -m astro_worker horoscopes generate`) for each
   sign, period and locale. The prompt contains only the facts and the style rules. The
   validator rejects output that fails the JSON schema or length limits, contains banned
   claims (guarantees, cures, death, accidents, investment calls; English and Hindi), or names
   a graha or sign that is not in the facts. One retry with the errors, then the entry is
   skipped and reported.
3. **QA queue**: entries are stored `pending_review`. A person approves (optionally editing),
   which publishes, or rejects with a reason. Each action is written to `audit_log`. The
   public API returns published entries only. Review happens in the admin app's QA queue or
   with `python -m astro_worker horoscopes review …` (the original bearer `ADMIN_TOKEN` was
   replaced by the admin role, ADR-0006).
4. **Pages never wait for prose.** Without a published entry, a page shows the computed facts
   and deterministic template sentences that restate them (template code, not an LLM), so no
   page is empty or thin and nothing unreviewed is published.
5. **Providers** sit behind one interface: `gemini` (default per PLAN.md §2), `anthropic`, and
   `fake` (dev/test only, refused in staging/production). Use paid tiers that do not train on
   inputs. Prompts carry no personal data; horoscopes are per sign, not per user.

## Consequences

- Publishing needs a reviewer every day: 36 entries a day per locale in steady state (12 daily
  + weekly and monthly on their boundaries). Schedule generation the evening before, IST.
- Changing the prompt bumps `prompt_version`; entries keep the version that produced them.
- Scores are explainable ("Saturn in your 11th house: favourable"), so editors can check prose
  against them.
